# 一次性 SSH 远程支持

作者：Ray Zhang。范围：`tools/ssh-tunnel`，2026-11-02。

该工具独立于 ARA Agent Core 和 LabSlot 业务。云端使用内存保存本次配对；1.1.0 增加 ICE/STUN 直连协商，直连成功时只保留云端控制连接，失败时中转 SSH 字节。主控可管理多个被控，被控启动一次只接受一个主控。现场账号密码留在现场 PowerShell 进程内，安装包没有共享私钥。

## 必须保留的边界

- 一次性配对码在云端原子领取，并绑定已经证明持有私钥的主控身份。知道设备 ID 不提供连接或关闭权限。
- 连接断开、主控退出或云端重启后，本次授权失效。恢复连接要重新启动和配对，不重放 SSH 命令。
- 目标主机公钥来自现场有效 SSH 配置和文件，主控按该公钥核验。外层服务器公钥通过经过证书验证的同源 HTTPS 获取。
- 隧道断开不等于现场授权文件已清理。正常退出撤销本次新增的公钥和规则；强杀、断电或未知安装状态可能需要人工根据回执清理，不能报告全部撤销。
- 远程安装依赖既有管理员共享和 WMI/DCOM。只有用户名和密码，无法在这些通道不可达时安装 SSH；离线入口也不能证明远程管理或入站访问已经可用。
- 安装或授权已提交但结果未知时，禁止与原操作并行清理或重放。重新操作前核对回执和进程状态。

## 已遇到的兼容问题

PowerShell 5.1 默认读取无 BOM 文本时可能按系统代码页解释，中文账号和路径会损坏。回执统一写 UTF-8，所有读取端明确指定 UTF-8。

OpenSSH 的 `UserKnownHostsFile` 同时解析空格和百分号。仅把它作为单个进程参数传递仍不够；路径需按 SSH 配置语法引用并转义 `%`。真实 `ssh.exe` 夹具覆盖这两个字符及错误主机密钥拒绝。

Nginx reload 后旧 worker 可能短暂处理旧路由。部署验收检查健康响应正文，不能把重定向到业务登录页当成中转上线。

## 安装交互

统一 EXE 使用标准 Windows 安装页面，只增加主控、被控两个单选项。选择决定桌面默认入口，开始菜单保留两者。没有自定义动效；安装完成与连接成功分开显示。静默参数 `/S /ROLE=controller|controlled` 只安装文件，不启动设备连接或修改 SSH 服务。

## 直连协议的边界（1.1.0）

配对回复的严格 JSON 结构保持不变。独立 `ry-direct-v1` SSH channel 承载一次有界 offer/answer；旧 hub/device 拒绝未知 channel 后可回退。不能用原 `request()` 做可选协商：其超时会关闭中转，SSH global request 的等待还会阻塞后续 stop/list。信令超时必须关闭自己的 channel，释放 hub 转发槽；底层未回复的 channel-open 每个设备最多一个，随会话结束收回。

Pion 的 detached DataChannel 是消息接口，SSH 是字节流。适配层保存短读后剩余数据，发送分成 16 KiB 消息，启用 SCTP 阻塞写以保持背压。半关闭在 SSH 子通道层处理。实际回归覆盖小缓冲读、跨消息的大载荷、共享流上限和取消。

直连 SSH 的设备公钥取自 hub 已认证的 device 身份；被控只接受原配对授权的 controller 公钥。直连与中转共用目标白名单和流上限，控制连接断开会关闭 PeerConnection、SSH 和目标 TCP。一次流已经尝试 direct open 后不转中转重试，避免重复目标拨号及未知外部操作；只有后续新流可以回退。

本次只验收本机真实 Pion/SSH 链路和受控故障，跨机器 LAN、不同公网 NAT、UDP 封锁现场与真实文件工具传输仍需分层验收。STUN 候选或 host/host 日志不能单独证明公网打洞。线上部署与安装包构建分别记录，不因生成新版二进制宣称线上已更新。

验证明细和未覆盖项见 [交付记录](../evidence/ssh-tunnel-20261102.md)。

## 星渡技能与退出码（1.1.1）

工具对外名称为星渡 Starferry，技能名 `starferry`，与 Reach Agent 区分；内核命令和已有安装入口保留。本机 Agent 用持续终端持有 controller 的标准输入，通过独立 SSH 进程操作目标。输入管道 EOF 会结束支持会话，不能用一次性 echo 管道代替持续控制端。

CASE-20261102-Starferry-device-exit：普通 device/controller 经过真实 hub 配对并完成双目标命令后，主控 quit 成功，但 device 返回 1。回读 x/crypto v0.57.0 的 SSH mux 确认：先关闭 incomingRequests，随后才唤醒 Conn.Wait。原代码在 Requests 循环结束后立即检查 ctx.Err，可能先于 Wait watcher 的 cancel，导致同一次关闭随调度返回 0 或 1。只等待进程结束、没有检查返回 error 的旧测试漏掉了该问题。

修复通过完成通道等待 Wait watcher 完成取消，再统一报告会话结束。当前协议不携带结束原因，因此退出 0 只表示隧道收尾，不能证明远端命令成功；握手、注册和授权阶段仍保留原错误。独立回归在修复前复现六项失败，修复后 relay/direct × stop/owner-close/hub-close 均返回 nil 并关闭活动流，授权拒绝仍返回原错误。针对性 race 2.908s、模块 race 19.153s 通过；无人工对照耗时，未计算效率提升。普通进程复验与部署状态续记在交付记录。
